# The connection-lifecycle baseline

`frontdoor/testdata/lifecycle-baseline.txt` records what the front door
observably does to a connection, one trace per scenario. This file explains
what it is for and the one rule that governs it.

---

## Why it exists

The front door's connection lifecycle is about to be moved behind an outcome
registry and a phase runner. That refactor is required to change no behaviour
at all — and "no behaviour changed" is a claim that needs something to be
checked against.

"All the existing tests still pass" is weaker than it sounds. A test suite
proves the properties somebody thought to assert. It does not notice that an
event moved, that a charge changed hands, or that a socket now closes without
the frame it used to send, unless a cell happened to look at that. The front
door has conformance and denial-taxonomy cells in abundance, but they are
distributed across twenty files and none of them is a statement of what a
whole connection's life looks like.

So the baseline is that statement, captured per scenario:

| Recorded | Why it is in the trace |
| --- | --- |
| **Wire bytes**, as named frames | Several paths are required to answer *nothing*. A trace that only recorded frames could not tell a deliberate silence from a dropped write. |
| **Ordered events** | The audit trail is what an operator reads after an incident. An event that moves is a change to what the record says happened. |
| **Close reason** | The same connection ending for a different stated reason is a behaviour change with no wire symptom. |
| **Charge delta** | Whether a refusal is charged to the source address decides whether a developer gets banned. It has no visible symptom until somebody is locked out. |
| **Resource accounting afterwards** | The ticket, the pre-auth slot, the control-lane reservation, the per-source entry and the tracking entry. The one that is not released is the one an anonymous peer farms by being refused. |
| **Engine calls, in one order across both seams** | A change that moved the cancel-key registration to the other side of the session open would leave every per-interface log unchanged. |

## When it was captured

At the parent of the refactor, and deliberately **after** the panic-containment
and charge-split work had landed. Taken before them, the baseline would have
frozen the classification that treated a full connection pool as a failed
login — and the refactor would then have been proven to preserve it faithfully.

## The rule

**It is not regenerated by the test run, and there is no flag that does it.**

A baseline a failing run can rewrite is not a baseline, it is self-approval:
the thing that drifted would be blessing the drift. Changing this file is a
hand edit, and it shows up in review as what it is — a change to the front
door's observable behaviour, stated in the diff.

`TestLifecycleBaseline_SemanticControls` sits beside the diff for a related
reason. A golden file proves that nothing changed; it never proves that what it
recorded was right. If the capture itself were wrong — an empty read mistaken
for a silent close, a charge counted against the wrong host — the diff would
defend that mistake forever. The controls fail on the *claim*, so a wrong
baseline and a changed baseline do not look the same.

## What is deliberately not pinned

Values that differ every run, because a baseline that fails for a reason nobody
cares about is a baseline everyone regenerates: the `BackendKeyData` process id
and secret, the peer's ephemeral port, and the credential presented during the
exchange. The trace records that a key was registered for a session, not which
key.

## A path that is deliberately absent

There is no trace for a capacity refusal rendering `53300`. That is a property,
not an oversight.

A capacity refusal says "the database is at its connection limit" instead of
the uniform "authentication failed" only when it carries a witness that it was
raised with a verified credential and a checked grant already in hand. The
engine mints that witness at the raise site and nowhere else, and there is no
constructor for it — one would let any caller forge the thing that decides
whether the front door reports live capacity to a stranger, which is exactly
what the witness exists to prevent.

The scenarios here drive a fake engine, and a fake engine cannot mint a witness
either. That it cannot is the property working as intended, so the trace stops
where the fake's reach stops. `frontdoor/capacity_disclosure_test.go` pins the
disclosure itself, and the live cells exercise it end to end when a test
database is configured.

## A finding this recorded

The shutdown trace is byte-identical to a normal client hang-up. Nothing on the
listener-close path sets a close reason, so the connection handler falls
through to its default and the trail reports `peer-closed` for a connection the
**server** ended. An operator reading the audit after a deploy sees a hundred
clients that supposedly hung up.

It is recorded rather than fixed. Changing it is an improvement, and it belongs
in a commit that is about that — not in a refactor whose entire value is that
it changes nothing.
